# GitHub 持續紀錄與部門知識回寫

這份流程把課堂、AI 日與日常工作的學習紀錄接到 GitHub。目的是看見同仁**怎麼使用、怎麼修正、怎麼成長**，再把經主管確認且能重複使用的做法累積成部門知識。課程滿意度和單次作業不能代替跨期紀錄。

本 Repo 是**公開**的。提交前必須依 [`PRIVACY_AND_SUBMISSION.md`](../PRIVACY_AND_SUBMISSION.md) 去識別化；真實姓名與匿名代號的對照表、原始對話、未公開業務資料都不放進 GitHub。若案例無法安全去識別化，保留在原本的工作環境，不提交本 Repo。

## 一次工作的路徑

1. **同仁完成真實工作**：沿用部門 AI 指令，先找資訊缺口，產出第一版，再指出問題並修正。若是模擬練習，明確標示。
2. **形成一筆學習紀錄**：使用 [`AI_LEARNING_REPORT_TEMPLATE.md`](../templates/AI_LEARNING_REPORT_TEMPLATE.md)。課程負責人在第一次提交時配給同仁一個不含身分線索的固定 `learner_id`，後續沿用；每次工作由提交者分配不同 `record_id`。AI 不知道代號時填「未提供」，不能猜。代號與真人的對照若有需要，只在 Repo 外由公司保管。
3. **主管在公開前檢查**：核對工作事實、成果狀態、修正證據與敏感資訊。主管未確認時，`reviewer_status` 保留「未驗收」；若不適合公開，不提交到本 Repo。目前 Repo 只有 Andy 有提交權限，因此先由有權限的人在主管檢查後代為提交。
4. **存入案例層**：將去識別化的紀錄存入 [`records/`](../records/README.md)。一項工作一檔；同一人的多筆紀錄靠 `learner_id` 串連，不把所有私人對話直接上傳。
5. **比較成長**：課程負責人與主管按相近工作情境查看同一人的多筆紀錄，先引用具體的第一次問題、修正動作和主管驗收，再判斷是否看見能力變化。只有一筆或情境差異太大時標「無法判定」；未提交不等於未使用。
6. **提煉知識**：主管確認某項做法可重複使用後，依 [`DEPARTMENT_KNOWLEDGE_ENTRY_TEMPLATE.md`](../templates/DEPARTMENT_KNOWLEDGE_ENTRY_TEMPLATE.md) 寫入 [`knowledge/`](../knowledge/README.md)，標出適用情境與來源紀錄。未確認的個人嘗試仍留在案例層。
7. **再次使用並修正**：新紀錄填入 `knowledge_used`，說明既有知識是否有幫助；若需更新知識，回到主管確認。這一步才證明知識庫開始幫下一次工作。

## 有提交權限者的 GitHub 步驟

1. 在原本的工作環境完成主管檢查與去識別化。公開分支與 Pull Request 不是私下審稿空間。
2. 從最新 `main` 建立工作分支，複製學習紀錄範本，填入 `records/<department>/<record_id>.md`；確認 `record_id` 沒有被用過。
3. 對照下方清單再檢查一次，提交到自己的分支並開 Pull Request。審核者核對欄位、來源與公開適宜性後才合併。
4. 知識條目另外提交到 `knowledge/<department>/`，附來源 `record_id` 和主管確認狀態。必要時回頭將原紀錄的 `linked_knowledge_id` 補上。

## 提交前檢查

- `record_id` 在 Repo 內不重複，`learner_id` 對同一人保持一致，但不能包含姓名、工號或可推回身分的資訊。對照表若有需要，由公司在 Repo 外保管。
- 已依隱私規則移除客戶、同仁、廠商與未公開營運資料；即使使用代號，若情境細節足以推知身分，也要再改寫或不提交。
- `case_type` 清楚區分真實去識別化與虛構練習；`final_status` 和 `reviewer_status` 不混用。
- `skill_evidence` 只寫有案例支持的觀察；沒有證據時寫「未觀察」，不把填表次數或滿意度當成能力。
- 欲升級為部門知識的規則已有主管確認，且可從知識檔回查來源紀錄。

## 推行範圍

先用已安排的小規模實測對象跑完「紀錄 → 驗收 → 知識回寫 → 再使用」，再決定各部門回報節奏與擴大順序。回報頻率仍由各部門主管確認，講師不自行替所有部門設定固定週期。
